# Domain conventions

This document fixes the E3 boundaries before persistence and CRUD are added.
Ship stores product concepts as desired state; Kamal is an execution adapter,
not the database model and not a concern of the browser.

## Ship-to-Kamal mapping

| Ship concept   | Kamal mapping                                                                                                   |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| Project        | Organization only; it has no direct Kamal key.                                                                  |
| Environment    | An isolated desired-state and deployment boundary. It is not a Kamal destination overlay.                       |
| Service        | One independently deployable Kamal root application with its own `service`, image, and generated configuration. |
| Server group   | A Kamal server role. A service targets one group in V1; the renderer may set it as `primary_role`.              |
| Domain         | Kamal proxy `host`/`hosts`; its port maps to `app_port` and its SSL flag maps to proxy SSL configuration.       |
| Accessory      | A Kamal accessory with a lifecycle separate from application deploys.                                           |
| Clear variable | An entry under Kamal `env.clear`.                                                                               |
| Secret         | A name under Kamal `env.secret`; its value is materialized only into Ship's restricted deployment workspace.    |
| Volume         | A host/container mount rendered in the format Kamal accepts.                                                    |
| Dependency     | Ship validation and orchestration metadata; it is not emitted as an invented Kamal key.                         |

The mapping follows Kamal's official configuration model:

- [configuration overview](https://kamal-deploy.org/docs/configuration/overview/)
- [servers and roles](https://kamal-deploy.org/docs/configuration/roles/)
- [accessories](https://kamal-deploy.org/docs/configuration/accessories/)
- [environment variables and secrets](https://kamal-deploy.org/docs/configuration/environment-variables/)
- [proxy, hosts, ports, and SSL](https://kamal-deploy.org/docs/configuration/proxy/)

Kamal roles run one application's image with role-specific placement and
commands. Ship therefore does not model each role as another application image.
Conversely, two Ship services with different images compile to two independent
Kamal application configurations.

Accessories are not updated automatically as part of an application deploy.
Ship must keep their boot/reboot lifecycle explicit. E3 may save an unplaced
accessory because server registration and role membership arrive in E4; the E5
validator must block deployment until placement resolves to a server or group.

Automatic proxy SSL is topology-dependent. E3 stores the requested hostname and
SSL state, while E5 validates whether the selected servers satisfy Kamal's SSL
requirements before rendering or deployment.

## Entity rules

- IDs are UUID v4 values generated by `internal/platform/identity`.
- Timestamps are UTC and serialized as RFC 3339.
- Names are trimmed, required, and limited to 100 Unicode characters.
- Slugs are lowercase ASCII, 1–63 characters, and match
  `[a-z0-9]+(?:-[a-z0-9]+)*`.
- A missing slug is derived from the name. Changing a name never silently
  changes an existing slug.
- Project slugs are unique per Ship installation.
- Environment slugs are unique within a project.
- Service and accessory names are unique within an environment.
- A service must define a repository or an image. A repository-backed service
  defaults its branch to `main` when omitted.
- Accessory types in V1 are `postgres` and `redis`. Placement may remain empty
  until E4, but an unplaced accessory cannot be deployed.
- Domain input is a hostname only: no scheme, port, path, query, or fragment.
  Hostnames are normalized to lowercase and unique within an environment.
- Volume destinations are absolute container paths. A volume belongs to exactly
  one service or accessory, and its source is unique within an environment.
- Clear variables and secret names use portable environment keys matching
  `[A-Z_][A-Z0-9_]*`.
- Dependencies have one source service and exactly one service or accessory
  target. Cycles are rejected.
- Deleting a project or environment is a hard cascade and requires a typed slug
  confirmation. Ship reports affected children before deletion.
- Environment cloning copies desired configuration atomically. Secrets are
  excluded by default and can be copied only through an explicit privileged
  request that re-encrypts them for the new scope.

## API boundary

The browser calls explicit Next.js handlers under `/api`. Those handlers only
forward an allowlisted request to the private Gin API. Gin resource paths remain
unversioned for V1, for example `/projects` and
`/projects/{projectId}/environments`.

Feature packages own their routes, service rules, and repositories. The API
command only constructs dependencies and calls `RegisterRoutes`; it does not
contain domain handlers.

List responses use one shape:

```json
{
  "items": [],
  "nextCursor": "opaque-or-omitted"
}
```

Malformed JSON returns `400`. Semantically invalid fields return `422` with the
shared validation envelope. Uniqueness and state conflicts return `409`.
Missing records return `404`. Every mutation requires the session-bound CSRF
token and exact configured origin.

Updates use `PATCH`. Destructive confirmation is part of the request contract,
not only a UI modal. Secret reveal is a CSRF-protected `POST`, never a cacheable
`GET`.

## E3 permissions

| Operation                                                                                | Permission              |
| ---------------------------------------------------------------------------------------- | ----------------------- |
| List or read projects                                                                    | `projects.read`         |
| Create, update, or delete projects                                                       | `projects.manage`       |
| Read environments and their desired-state graph                                          | `configuration.read`    |
| Mutate environments, services, accessories, domains, volumes, variables, or dependencies | `configuration.manage`  |
| List secret names and metadata                                                           | `secrets.metadata.read` |
| Create, replace, or remove secrets                                                       | `secrets.manage`        |
| Reveal secret plaintext                                                                  | `secrets.reveal`        |

Owner and admin may manage projects and configuration. Deployer and viewer may
read them. Existing secret and deployment permissions remain more restrictive.

## Persistence boundary

PostgreSQL is the only source of truth for E3 desired state. Redis must not hold
projects, environments, services, accessories, domains, volumes, variables,
secrets, or dependencies. Redis remains limited to sessions, rate limits, jobs,
locks, cache, and transient events.

Schema structs, constraints, and the ER diagram are step 2. This document does
not introduce E3 tables or CRUD behavior.
